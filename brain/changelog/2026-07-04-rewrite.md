## Addendum 7 — migrations wired into build (no API trigger needed)
User asked for "an API trigger" to run the migration. Pushed back: a
hand-rolled endpoint that shells out to the Prisma CLI from inside a
serverless function is fragile and an unnecessary attack surface for a
destructive DB operation. The correct fix is `prisma migrate deploy` in
the build command itself — Vercel already has DATABASE_URL at build time.

- Generated the actual migration files offline via
  `prisma migrate diff --from-empty --to-schema prisma/schema.prisma --script`
  (no live DB needed for this — first real migration files this project
  has ever had; migrate deploy had nothing to apply before this).
- `prisma/migrations/20260704000000_init/` + `migration_lock.toml` committed.
- build script: `prisma generate && prisma migrate deploy && next build`
- **Verified against a real local Postgres, not assumed:**
  - Fresh/empty DB (simulating current real Neon state) → ran the exact
    build command → all 6 tables created, build succeeded
  - Re-ran build against already-migrated DB → "No pending migrations
    to apply", build succeeded (idempotent, safe to run every deploy)
- Note: `@prisma/adapter-neon` (used by the app's PrismaClient at runtime)
  requires Neon's WebSocket transport and can't connect to plain local
  Postgres — irrelevant here since `migrate deploy` uses its own direct
  connection, independent of that adapter. Confirmed by testing both paths.
- Tradeoff accepted deliberately: if DATABASE_URL is ever wrong/unset,
  the BUILD now fails loudly instead of deploying a broken app that 500s
  on every real user, which is what happened to the 51 failed registrants.

## Addendum 8 — the "wire it into build" deploy actually failed (P3005 + PK collision)
Real Vercel deploy of the previous commit FAILED — pulled the actual build
log, didn't assume success from a git push. Two real, sequential problems,
each reproduced and fixed against a real local Postgres seeded to match
the true production state (legacy `students` table + its indexes):

1. **P3005** — `prisma migrate deploy` refuses to run against a database
   with ANY untracked existing objects (safety check). Your real Neon DB
   still has the old Express app's `students` table, never renamed.
2. **After fixing #1** (renaming to students_legacy) — `students_pkey`
   already existed as a leftover of the OLD table, because Postgres does
   NOT rename a table's constraints when the table itself is renamed. The
   new schema's own `students` table failed to create with "relation
   students_pkey already exists". Fixed `00-preserve-legacy.sql` to also
   `RENAME CONSTRAINT students_pkey TO students_legacy_pkey`.

**This requires ONE manual, one-time step on the real Neon DB — cannot be
safely automated into the build**, because auto-baselining on every build
would be actively dangerous against a genuinely fresh database (it would
mark migrations "done" without ever creating the tables). Do this once:

```
psql "$DATABASE_URL" -f scripts/00-preserve-legacy.sql
npx prisma migrate resolve --applied 20260703000000_baseline_legacy_db
```

After that one-time command, every future `git push` self-heals the
schema automatically via the build step — proven end-to-end against a
seeded-to-match-production local Postgres: legacy table renamed, PK
constraint renamed, baseline resolved, `npm run build` (the literal Vercel
command) ran migrate deploy successfully, all 6 new tables created,
students_legacy data intact and unmodified, second build run idempotent
("No pending migrations to apply").

## Addendum 11 — /dashboard 404, an auth-bypass gap, and a crash bug (all caught by testing)
Login succeeded (seed worked against real Neon — confirms Addendum 10's
unverified gap is closed) but landed on a 404: login defaults to
redirecting to `/dashboard`, and no page existed there — only its
subroutes did.

**More serious than the missing page**: the proxy's route-matching only
checked known prefixes (`/dashboard/super`, etc.). Bare `/dashboard` matched
NONE of them, so it fell through with `NextResponse.next()` — a real
authentication bypass, not just a missing page. Anything ever placed
directly at `/dashboard` would have been served with zero auth check.

Fixed:
- Added `/dashboard` as an exact-match entry requiring any authenticated
  role, closing the bypass.
- Added `/dashboard/denied` as an explicit pass-through (it's the target
  of role-check redirects, so it can't itself require passing one).
- Added `src/app/dashboard/page.tsx` — role-routes to the right home.
- **Caught a real crash while testing the above**: `session?.user.role`
  (and 3 other identical instances across school/mentor dashboards +
  add-school action) only guards `session` being undefined, not
  `session.user` — throws if `user` is ever undefined on a truthy
  session object. Found via an actual 500 on `/dashboard/denied` during
  testing, not code review. Fixed all 4 instances to `session?.user?.role`.
- Verified live: unauthenticated `/dashboard` → 307 to `/login`; `/dashboard/denied` → 200 (was 500 before the fix).

RUN_LEGACY_BASELINE and RUN_SEED have both done their jobs — user

## Addendum 13 — real root cause: UntrustedHost, not just the secret scoping
User reported the actual symptom clearly: login succeeds, but navigating
to the dashboard URL shows the login page again — not a 404, not a crash,
a silent bounce-back. That's the tell for Auth.js treating the session as
invalid rather than a config/schema error.

Confirmed via Auth.js's own documentation (authjs.dev/getting-started/deployment)
and multiple corroborating sources: `UntrustedHost` errors on **custom
domains** (innovate.alfinega.com is not *.vercel.app) can make `auth()`
unable to verify a session inside `src/proxy.ts`, even when a valid login
cookie exists — because the host-trust check runs as part of session
resolution itself. This matches the earlier local reproduction exactly:
`[auth][error] UntrustedHost` fired specifically from `/middleware` in that
test, mirroring the real production error groups seen in Vercel's runtime
logs (`routes=/login, /middleware`).

Fixed: added `trustHost: true` to the NextAuth config. Verified the exact
local scenario that produced UntrustedHost before (hitting a dashboard
route via `next start`) no longer produces it after the fix — confirmed
by grepping server output, not assumed from reading the docs alone.

This is very likely the actual root cause of "login works, dashboard
shows login again" — more specific and more likely than the AUTH_SECRET
Production-scoping theory from Addendum 12, though that fix (explicit
`secret:`) is also correct and stays.

## Addendum 14 — ROOT CAUSE FOUND: AUTH_SECRET genuinely missing from Production
User pushed back correctly: "no observable change, still the same." Both
the trustHost fix (Addendum 13) and the explicit-secret fix (Addendum 12)
were real, correct fixes for real issues, but neither was THE cause of
the reported symptom. Traced properly this time instead of theorizing:

1. Reproduced the full auth flow end-to-end locally (csrf → credentials
   callback → protected route) against a freshly seeded real account —
   not assumed, actually executed with curl + a real bcrypt-hashed user.
2. This surfaced a local-only red herring (`CallbackRouteError` from the
   Neon adapter not working against local Postgres — expected, documented
   earlier, irrelevant to production).
3. **Checked production runtime errors again, properly this time**: found
   `MissingSecret` STILL firing — 25 occurrences, 8 users, most recent
   only ~4 minutes before checking, on the deployment that already
   included the `secret: process.env.AUTH_SECRET` fix. This is
   conclusive: the explicit-secret code fix cannot help if the
   environment variable itself is empty in Production — and this proves
   it genuinely is. This is almost certainly THE actual root cause of
   "login succeeds, dashboard shows login page again": auth() can't
   verify any JWT without a secret, so every session check silently
   fails and every protected route bounces to /login, indistinguishable
   from "never logged in."

**Fix**: `scripts/check-env.js`, wired as the FIRST build step. Fails the
build immediately and loudly (exit 1, explicit message naming exactly
which var is missing and how to fix it in Vercel's dashboard) if
DATABASE_URL or AUTH_SECRET are missing or AUTH_SECRET is suspiciously
short. This is the same philosophy as the migration guard: a misconfigured
deploy should refuse to ship, not silently go live broken for real users.
Verified all three cases (missing / too-short / valid) behave correctly.

**User action, unavoidable, browser only**: Vercel dashboard → Settings →
Environment Variables → AUTH_SECRET → delete and re-add if unsure →
CONFIRM the "Production" checkbox is checked → generate a real value with
`npx auth secret` if the current one is a placeholder → Save → redeploy.
This is now enforced: the next deploy will refuse to build at all if this
isn't done, with an unmissable error explaining why.
