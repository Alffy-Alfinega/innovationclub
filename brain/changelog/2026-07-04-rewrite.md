## Addendum 7 — migrations wired into build (no API trigger needed)
User asked for "an API trigger" to run the migration. Pushed back: a
hand-rolled endpoint that shells out to the Prisma CLI from inside a
serverless function is fragile and an unnecessary attack surface for a
destructive DB operation. The correct fix is `prisma migrate deploy` in
the build command itself — Vercel already has DATABASE_URL at build time.

- Generated the actual migration files offline via
  `prisma migrate diff --from-empty --to-schema prisma/schema.prisma --script`
  (no live DB needed for this — first real migration files this project
  has ever had; migrate deploy had nothing to apply before this).
- `prisma/migrations/20260704000000_init/` + `migration_lock.toml` committed.
- build script: `prisma generate && prisma migrate deploy && next build`
- **Verified against a real local Postgres, not assumed:**
  - Fresh/empty DB (simulating current real Neon state) → ran the exact
    build command → all 6 tables created, build succeeded
  - Re-ran build against already-migrated DB → "No pending migrations
    to apply", build succeeded (idempotent, safe to run every deploy)
- Note: `@prisma/adapter-neon` (used by the app's PrismaClient at runtime)
  requires Neon's WebSocket transport and can't connect to plain local
  Postgres — irrelevant here since `migrate deploy` uses its own direct
  connection, independent of that adapter. Confirmed by testing both paths.
- Tradeoff accepted deliberately: if DATABASE_URL is ever wrong/unset,
  the BUILD now fails loudly instead of deploying a broken app that 500s
  on every real user, which is what happened to the 51 failed registrants.

## Addendum 8 — the "wire it into build" deploy actually failed (P3005 + PK collision)
Real Vercel deploy of the previous commit FAILED — pulled the actual build
log, didn't assume success from a git push. Two real, sequential problems,
each reproduced and fixed against a real local Postgres seeded to match
the true production state (legacy `students` table + its indexes):

1. **P3005** — `prisma migrate deploy` refuses to run against a database
   with ANY untracked existing objects (safety check). Your real Neon DB
   still has the old Express app's `students` table, never renamed.
2. **After fixing #1** (renaming to students_legacy) — `students_pkey`
   already existed as a leftover of the OLD table, because Postgres does
   NOT rename a table's constraints when the table itself is renamed. The
   new schema's own `students` table failed to create with "relation
   students_pkey already exists". Fixed `00-preserve-legacy.sql` to also
   `RENAME CONSTRAINT students_pkey TO students_legacy_pkey`.

**This requires ONE manual, one-time step on the real Neon DB — cannot be
safely automated into the build**, because auto-baselining on every build
would be actively dangerous against a genuinely fresh database (it would
mark migrations "done" without ever creating the tables). Do this once:

```
psql "$DATABASE_URL" -f scripts/00-preserve-legacy.sql
npx prisma migrate resolve --applied 20260703000000_baseline_legacy_db
```

After that one-time command, every future `git push` self-heals the
schema automatically via the build step — proven end-to-end against a
seeded-to-match-production local Postgres: legacy table renamed, PK
constraint renamed, baseline resolved, `npm run build` (the literal Vercel
command) ran migrate deploy successfully, all 6 new tables created,
students_legacy data intact and unmodified, second build run idempotent
("No pending migrations to apply").

## Addendum 9 — no-CLI bootstrap, not a public API trigger
User has no PC and asked for a browser-triggerable API URL to run the
migration. Declined that specific shape: a GET-triggerable endpoint that
mutates production DB state is dangerous regardless of a secret param
(prefetch, bots, double-clicks, no confirmation step) and would still
require pasting DATABASE_URL into chat — same exposure class as the PAT
already flagged repeatedly this session.

Built the actual need instead: scripts/maybe-baseline.js, gated by a
Vercel env var (RUN_LEGACY_BASELINE=yes-run-once), wired into the build
before `prisma migrate deploy`. No new secret required — uses the
DATABASE_URL Vercel already has. No CLI needed on the user's end — Vercel
dashboard (Settings → Environment Variables) works from any browser.

Verified three scenarios against a local Postgres seeded to match real
production legacy state:
- (A) flag unset → skips baseline, fails P3005 as before (safe default,
  matches current real deploy state, no accidental trigger)
- (B) flag set → renames legacy table + PK constraint, resolves baseline,
  migrate deploy creates all 6 new tables, legacy data intact, build green
- (C) flag left ON for a subsequent build → idempotency guard checks real
  `_prisma_migrations` state (not just the env var) and skips cleanly,
  build still green — safe even if the user forgets to remove the flag

User action required (browser only, no CLI):
Vercel dashboard → innovationclub project → Settings → Environment
Variables → add RUN_LEGACY_BASELINE = yes-run-once → Redeploy → once
green, delete the variable (optional cleanup, not required for safety).
